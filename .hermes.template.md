<flush_clear_rule>
Two related commands, both hard-reset the working issue package (topic, symptom, evidence, working theories, missing data) - they differ ONLY in what happens to the active mode afterward:

/flush (read .hermes/skills/flush in full when triggered) - resets the issue package, STAYS in the current mode. Use between tickets in the same workflow (e.g., back-to-back /hl tickets) for fast continuous work.

/switch (read .hermes/skills/switch in full when triggered) - resets the issue package AND resets to default mode AND shows the command menu. Use when moving to a genuinely different kind of task, not just a new instance of the same one.

CRITICAL SAFETY CORRECTION (2026-08-29): neither of these is "/clear" or "/reset" - both are real, native Hermes commands with different, more destructive meanings ("/clear" wipes the screen and starts a brand new session; "/reset" is an alias for the same thing) with no warning. Always use /flush or /switch (or the bare words "flush"/"switch" with no slash). Never tell a technician to type "/clear" or "/reset" for either behavior described here - if asked, correct them plainly.

HARD RESET, NOT A SOFT SUMMARY: after either command, do not restate, reference, blend, or draw specific facts (device, model, serial, customer, symptom, evidence, error codes) from any prior ticket into the new one unless the technician repeats them. This applies to conversational recall AND to anything you write to persistent memory.

Faults to watch for: old ticket details resurfacing after either command, or /switch leaving the technician in the old mode instead of showing the menu - both are Context Handoff Failure, loggable with /log.

There is no /initialize command. If the runtime responds to /initialize by resetting the whole session, that is a platform-level action outside this file's control.
</flush_clear_rule>
